## 1. なぜ必要か

R10〜R15 のループ（2026-07-30〜31）の実測が、実行の記録に残る空白と、実態と食い違う門を示した。

**語彙が二重に定義されていること。** prompt は判定 3 語（APPROVE / REVISE / REJECT）を逐語で指定し、外れれば判定なしになると予告している。ところが受け入れ側は今も 3 判定に対して計 16 の語形（LGTM、NO-GO、SHIP IT、NEEDS WORK 等）を受ける。書いてよいと予告した語彙と、読むときに受ける語彙が別々に定義されている限り、その差は食い違いとして残り続ける — R11 は手で二重に持たれた語形表が 30 形中 8 形でずれていることを、R12 はそのずれを見張るはずの等価性テストが盲目であることを、それぞれ P0 として示した。

**閾値到達が結論の位置を占めていること。** 現行の記録は閾値到達を実行の結論の位置に置く。しかし実際のループはそれで閉じていない。R4 の到達は 42 文字の空返答による賛成を含んでいたため根拠にされず、v0.6 も R10〜R15 も (a)+(b) の消尽と操作者の freeze 宣言で閉じた。さらに、言い過ぎを残余として明記する正直な改訂が賛成数を下げる観測（1/5 → 0/5、2026-07-27）があり、数値の門は正直さを罰する側に立っている。実態と食い違った門が結論欄を占めることは、記録を読み誤らせる。

**母数に空白があること。** persona 提出の拒否→言い直しは、最初から少人数だった実行と記録上区別できない。提出されない persona の扱いは v0.6 §6 で未決のまま名指しされていた。食い違い枠の票を除いた集計は運用（数えない）だけがあって記録にない。輸送の診断のうち API エラーと fast mode の状態は adapter が返すようになったのに記録へ通らない（応答した実モデルは既に記録へ届いている）。実行が何に合格しようとしたか（事前宣言 spec）も記録に残らない。

**配布が一様であること。** `claude_cli` 枠は `review_context: 'independent'` の既定で sandbox 実行になり、リポジトリを読めない（実測確定、2026-07-31）。R12〜R15 の「パス＋sha256 で原本を読め」という一様な配布は、この枠には実行不能な指示であり、薄い返答という形で母数だけを痛めていた。

## 2. 不変条件

- **INV-R1（語彙の単一性）** — 判定として書いてよいと予告される語彙と、判定として読まれる語彙は同一であり、APPROVE / REVISE / REJECT の 3 語（とその時制・活用違い）だけからなる。SKIP を含め、特例となる語は存在しない。語彙の外の語で判定を試みた提出の帰趨は、その提出が言い直せるかどうかに従う: 終局の提出（外部枠の返答）は判定なしとして母数を出て、書かれた語が事由として記録に残る。言い直しうる提出（persona の提出 — 著者は呼び出し元）は受理されずに差し戻され、差し戻しがあったことは INV-R4 の意味で記録から読める。
- **INV-R2（比率の参考値化と結論の不在）** — 比率と閾値到達は記録される参考値であり、実行を閉じる判定ではなく、実行の記録において結論の位置を占めない。結論は操作者の宣言（freeze / もう一周）として記録 schema の外にあり（裁定 2026-07-31: 判断の層は機構化しない。裁定は現行どおり L2 / handoff に記録される）、記録は観測を提示するにとどまる。v0.6 INV-E2 の母数規則は座席の語彙でそのまま生きる: 母数に入るのは実質を伴う判定を運んだ座席だけであり、座席の実質は、その座席の提出の全体 — 外部の座席では返答、persona の座席では受理の門（INV-R1）を通った行の集合（いずれかの行が実質を伴えば、座席は実質を伴う）— で測られ、無応答も実質の不在も、要求される一致数を押し上げない。この測り方は現行の実質判定と同じ広さであり、狭めも広げもしない。その数の意味だけが門から参考値へ降りる。これは v0.6 §5 が変更せず既存の運用に残した「到達しない場合の閉じ方」の条文化の一歩外（到達した場合の閾値も結論の座を降りること）に及ぶ変更であり、ここにその申告を置く。
- **INV-R3（persona の座席と行）** — 実行に招集される persona の集合 — 体数と、チームとしての実行モデルの申告 — は、投函の時点で申告され、その実行の記録に入る。枠との照合の鍵はこのチーム単数の申告であり（v0.6 INV-P2 の「その実行モデルと一致する枠」の読み方はこれで変わらない）、体ごとのモデルの申告は行の記録に載るだけで照合には関与しない。persona の提出は 1 体ずつ独立の行として記録される。行のモデル名が申告に由来することは記録から読め、申告に由来する名は観測に由来する名と同じ位置に置かれない（v0.6 INV-P1 を条文として引き継ぐ）。母数の単位は座席 — INV-P2 が正本の枠と申告から一意に定める観測者集合の要素 — であり、persona チームはその一つを占める（一致する枠があればそのうちちょうど一つ、なければ独立した観測者として）。行は座席の内部記録であって票の数ではなく、座席が参考値の集計に運ぶ判定が行からどう導かれたかは記録から読める（導出規則の選択は機構であり backlog。現行の優先順位規則を既定とする）。
- **INV-R4（母数の完全事由）** — 母数を動かした事由はすべてその実行の記録から読める。事由の類型を本設計は列挙しない — 閉じた列挙は漏れを製造する（R1 レビューで、実質を伴わない返答・呼び出し元による枠除外・増設・配布形式の不在の 4 類型が列挙から漏れた実例による）。母数の単位は座席であり（INV-R3）、母数の構成 — どの座席が入り、入らなかった座席はなぜか — は座席の列として記録から一意に復元できる。persona の個体の欠席は行の事由として記録されるが、母数を動かすのは座席が実質を伴う判定を運ばない場合だけである — INV-E2 の二つの事由（無応答・実質の不在）を座席の単位で言い直したものであり、実質の測り方は INV-R2 による（裁定 2026-07-31 の「未提出 persona は期限で無応答へ」を座席の単位で読み直したもの。読み直しは同日の第 2 裁定で承認。collect 期限内は同じ prompt での再走が許される）。実行の記録は、その実行が完結する時点で構成される — persona の招集がない一段の実行（v0.6 INV-P2）では応答の返却、二段の実行では collect の成立。collect の成立とは、collect の呼び出しが受理されたことをいい、受理によって最終の記録が構成される。招集した観測者が全員揃っていることは受理の要件ではない — 揃わなかった座席は前掲の規則で母数を出て、事由が残る。無応答の確定は受理の時点で起きる: 期限は再走の許される幅を区切るだけで、確定の時点ではない。現行の受理の門は 2 体未満の persona 提出を受けない体数の下限を持つため、この段落はその変更も要求する — その申告をここに置く。実行の存在の印は投函の時点で書かれ、完結の記録がそれを置き換える。完結しない実行では、この印と判明している範囲の事由が、そのまま最小の痕跡として残る — 痕跡を書く主体を期限の観測に頼らせないための順序である（印の形と保持の期間は機構であり backlog。現行の掃除機構は期限超過の pending を削除するため、この一文は現行挙動の変更を要求する — その申告をここに置く）。受理の門で差し戻された persona 提出（INV-R1。差し戻しは受理側の出来事であり、系の観測として記録される — 呼び出し元の申告ではない）は、それ自体が母数の事由の位置を占めることはない。実質の測定は受理の門を通った行の集合の上で行われる（INV-R2）ので、差し戻しが母数に影響するとすれば、それは受理された集合の変化を経由する INV-R2 の変動であり、その経緯は記録から読める。現行の粒度（呼び出し全体の差し戻し）では差し戻しの時点で受理された集合が構成されないため、母数は動かない。差し戻しがあったことと事由は、同じ実行の成立した記録から読める（実行が完結しなかったときは前掲の痕跡に従う）。差し戻しの粒度 — 語彙の外の行だけを差し戻すか、呼び出し全体を差し戻すか — は機構であり backlog に置く（現行は呼び出し全体）。いずれの粒度でも、差し戻しの事実と事由が読めることは変わらない。
- **INV-R5（食い違いの併記）** — 判定の成立には語彙の判定（INV-R1）と実質の判定（INV-R2）が先行する: 本条は、実質を伴う判定を運んで母数に入った座席にのみ関わる。適用は、応答から実際のモデルを取り出せる輸送の座席に限る（v0.6 INV-E5 のとおり。persona の行のモデル名は申告に由来し、食い違いはそこでは定義されない）。その上で、要求したモデルと応答したモデルの食い違いが検出された座席の判定は母数にとどまり、それを除いた集計が併記される。食い違いは母数を動かす事由ではない — 母数から外せば、検出の記録と判定の消失が絡んで、どちらの集計も読めなくなる。どちらの集計も INV-R2 の意味で参考値である。v0.6 §6 の未決「記録するにとどめるか、母数から外すか」を、本設計は「とどめ、除外集計を併記する」で閉じることを提案する。
- **INV-R6（実行の自己記述）** — 実行が何に合格しようとしたか（事前宣言 spec への参照と、その同一性の確かめ方）と、輸送の診断（応答した実モデル・API エラー・fast mode の状態）は、その実行の記録から読める。
- **INV-R7（配布の到達性）** — 配布とは、系が成果物を座席へ運ぶ行為を指す。呼び出し元の harness の内側で原本を参照する座席（persona チーム）には配布の行為が存在せず、本条はその座席に適用されない。配布を要する座席について: 成果物の配布形式は、その実行の記録において座席ごとに読める属性である（既定を正本の枠に置くか座席の種別から導くかは機構であり backlog）。座席がその形式で成果物へ到達できない配布は、無応答を配布側が製造する行為として禁じられる。配布できる形式が一つも無い座席は、観測者集合には残り（集合の決定は INV-P2 のまま正本の枠と申告による）、配布されない。配布されなかったことと事由は記録に残り、その座席は母数に入らない。配布されなかった座席に INV-R4 の欠席の扱いは適用されない — 配布されなかったことが、その座席の唯一の帰趨である。

INV-R1 と INV-R2 は互いを条件とする。門の下では、語彙の外の語を書いた外部枠が母数を出ることは票の静かな喪失だった。参考値の下では、それは判定表に「語彙外の語を書いたので判定なし」と載る報告対象になり、損失ではなく信号になる。語彙を絞る変更を単独で入れてはならない理由はここにある。

## 3. 較正と重み付け

較正（どの枠がどの領域で価値観由来の指摘を出しやすいか）による票の自動重み付けはしない。重み付けは信号を隠す種類の調整であり、INV-R2 が門を外した後は必要もない。較正は L1 `multi_llm_reviewer_evaluation` の履歴として表に出し、操作者の判断がそれを引用する。

## 4. 非目標

- 判断の層の機構化。orchestrator の推奨と操作者の裁定を実行記録の欄にすることは、裁定（2026-07-31）によりしない。agent への委譲を設計する日に再訪する（別題。その場合も操作者の裁定を最終に置く構造は残す）。
- 較正による自動重み付け（§3）。
- 遡及。既存の記録の変換はしない。本設計は新しく始まる実行にのみ及ぶ。
- 食い違い検出時の再呼び出し。adapter の封筒読み誤り（`keys.first`）が修正された今、単一鍵で食い違いが発火した実例が出るまで保留する。
- 環境変数 `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` による内部呼び出しの抑止。因果が未証明であり、依存すれば診断の証拠も消える。
- persona チームの編成への干渉、申告の真偽検証（v0.6 の非目標のまま）。

## 5. Open Unknowns（宣言）

- 拒否された提出の記録に載せる中身の範囲 — 事実と事由だけか、拒否された本文も保存するか。保存は診断に効くが、記録の分量と、言い直し前の文面を残すことの意味（persona の提出は呼び出し元が著者）に関わる。
- 記録 schema の版の表し方 — 新旧の記録を読み分ける印をどう置くか。遡及はしない（§4）ので、これは書き手ではなく読み手の問題である。

## 6. backlog（実装時に選ぶ機構）

- WORDS 縮小の具体（時制・活用違いの範囲。padding 規則と `stated()` の全値一致は現行維持）。
- 拒否の追記の機構（collect の flock 保持中の sidecar 追記、成立した collect の最終 payload 上の表現）。
- 除外集計の欄名と置き場。
- 診断欄の通し方（review_serializer / dispatcher 各 1 行）と、診断欄の中身の格（状態の札か本文か — 資格情報や本文を記録へ運ばない側に倒す）。
- spec 参照の置き場（token・最終 payload）と同一性の表現（パス＋sha256）。
- 到達可能性の計算時点。
- JSON `overall_verdict` 重複鍵の門（R12 P1）。
- `artifact_delivery: inline | by_reference` 属性の表現と、観測者ごとの記録への解決のしかた（既定の置き場を含む）。
- 参考値化に伴う既存の結論欄（consensus verdict 相当）の改名か注記か。
- persona 座席の判定を行から導く規則（現行の優先順位規則 REJECT > REVISE > APPROVE を既定とする）。
- 完結しなかった実行の最小の痕跡の形・保持期間・書き込み点（INV-R4 が痕跡の存在を要求する。現行は非同期経路のみ投函時に印を書き、掃除機構は期限超過の pending を削除するため、実装は書き込み点の統一と掃除規則の変更を伴う）。
- 受理の門の体数下限の扱い（現行は 2 体未満の persona 提出を受けない。INV-R4 が変更を要求する）。
- 差し戻しの粒度（行ごとか呼び出し全体か。現行は呼び出し全体）。
- schema 版の印の具体（§5 の未知の機構側）。

## 8. freeze の根拠

R1 から R6 まで 6 ラウンドの multi-LLM review を経た。P0 の生数は 20 → 11 → 9 → 6 → 1 → 0 と単調に減り、(b)（設計規律からの逸脱）は R3 以降 4 ラウンド連続ゼロ、R6 では全観測者が APPROVE を返した（機械集計 4/4。空返答型 APPROVE を除いた実質でも 3/3 — claude_cli は 6 ラウンド連続の実質票、cursor は R4 以降 3 連、persona 座席は 3 体一致）。R5 で最後に残った (a)（差し戻しの母数中立性が粒度の選択に依存する）は、受理の門を通った行の集合を測定の土台と定める R6 の修正で閉じ、指摘した観測者自身が同じ攻撃走行の再実行で閉じを確認した。残る指摘はすべて (c)（価値観由来の助言）であり、§6 backlog と実装ラウンドの queue に置き場が名指しされている。freeze の根拠は比率の到達ではなく (a)+(b) の消尽である — 本設計の INV-R2 が条文化した閉じ方に、本設計自身が従う。宣言は操作者（masaomi、2026-08-01）による。ループの記録と裁定履歴は L2 `handoff_mlr_v07_design_loop_r1_to_r6_freeze_candidate_20260801`。
