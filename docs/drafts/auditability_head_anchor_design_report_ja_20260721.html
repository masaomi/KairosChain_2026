1. なにが問題だったか — 現行 anchor が証せない三つのこと

企業が社内の閉じた（内容非公開の）KairosChain で計算を記録し、公開サーバーへ anchor して 「確かに計算し、記録し、改竄していない」を第三者に示したい——この使い方を想定すると、 現行の anchor（文書の指紋ひとつを載せるだけ）には次の穴があります。

証したいこと現行理由
一員性 — その指紋が内部鎖のメンバーであること✗ anchor は指紋単体しか見ない。鎖と無関係な単発の指紋でも見た目が同じ
不改竄 — 内部鎖が書き換えられていないこと✗ 内部鎖は非公開・単一運営者。外からは検査できない
位置と順序 — 追記の何番目か、どちらが先か✗ 位置の情報が公開されない

2. 中心のアイデア — 束縛対象の格上げ

一言でいうと anchor に「文書の指紋」ではなく「内部鎖の全履歴への封印（累積 commitment）」を載せる。 監査人には鎖そのものを見せる代わりに、証明書（包含証明・consistency 証明）だけを渡す。 内容は一切開示されない。

3. 包含証明 — 「第 N 番の一員」を中身を見せずに証す

封印（root）は Merkle 木で作られます。監査人に渡すのは、当該記録の指紋から root まで登る経路上の 「隣のハッシュ」の列＋位置情報だけ。隣の記録の中身は一切渡りません（MPR-2）。

4. consistency 証明 — 「鎖は書き換えられていない」を支える一本柱

包含証明だけでは、運営者が「履歴を作り直して新しい封印を anchor する」攻撃を検出できません。 一つひとつの証明は新しい封印に対して正しく検証できてしまうからです。 そこで MPR-9: 同じ鎖 identity を持つ二つの封印は「後が前のそのままの延長である」ことを consistency 証明で検証できなければならない、と定めます。

5. 三者の構図 — なにが公開され、なにが closed のままか

6. 9つの invariant（MPR-1〜9）早見表

ID名前一言でいうと
MPR-1束縛の commit と一貫性 head binding は entry_hash の中（差し替えは発覚する）。新規 entry のみ付与で AHM-4 保全。検証できない要素は「情報」と正直に表示し、証明の信用を借りない
MPR-2隣の封じ込め 証明が運ぶのはハッシュと構造情報のみ。中身は越境しない（低エントロピー時の残余は開示）
MPR-3自己記述の決定性 検証の作法（規約）に名前を付けて commit し、定義自体も検証可能に。葉と中間節の取り違え偽造を性質として排除
MPR-4監査人の自足性＋信頼基盤の開示 検証は5入力で完結・鎖アクセス不要。ただし「作るのは運営者」「commitment≠中身」の線引きを内蔵
MPR-5存在は証す・網羅は証さない anchor しなかった計算は見えない。結果非依存で anchor する規律は L2 の仕事と明記（正直な限界）
MPR-6証明の射程 一員性・不改竄・位置・順序まで。品質・正しさは語らない（それは L3/L4）
MPR-7最初の anchor 以前は時刻の裏付けなし 古い記録も一員性は証明できる。証明できないのは記録時刻。anchor が密になるほど以後の窓は狭まる
MPR-8位置の commit と順序 証明は位置と列の長さを commit。「第 N 番」が言え、順序は位置の引き算。時計は使わない
MPR-9anchor 間の整合 同一 identity の封印同士は延長関係を検証可能に。非提出は「未確立・報告対象」（有罪ではない）

7. 成長経路 — この設計が「やらない」と決めて次段階へ送ったもの

正直な限界（設計に内蔵された開示）
  • anchor log 自体を丸ごと差し替える攻撃は L1 では検出できない（→ L2 が塞ぐ）
  • 「都合の悪い計算を最初から anchor しない」は監査人に見えない（→ 結果非依存の規律は L2）
  • 証明は計算の「正しさ」を語らない（→ 再実行は L3、検証可能計算は L4）
  • 最初の anchor より前の記録は、一員性はあるが時刻の裏付けがない（MPR-7）

7-補. 将来ステップ L2/L3/L4 の詳細と進め方の方針（2026-07-21 追記）

前節の階段（図5）の各段について、「どの穴を・どう塞ぐか」をもう一段噛み砕いて記録する。 前提として押さえるべき関係: L1 は証明の「形」を完成させた。L2〜L4 は同じ証明が「信じられる条件」を 積み増すだけで、L1 の証明機構（封印・包含・consistency・位置）は以後どの段でも作り直さない（凍結 §5）。

L2 — head の外部公開と cadence（ANC-4/6）

  • 塞ぐ穴: ①anchor log 自体の丸ごと差し替え — 公開 anchor log も単一運営者のサーバー上のファイルなので、 内部鎖を書き換えたうえで anchor log ごと整合するよう作り直せば、監査人には「最初からそうだった」ようにしか見えない （ANC-1 が scope X の正直な残余として開示・MPR-4/9 が「L2 で閉じる」と明記）。 ②見せ分け（split-view） — 監査人ごとに別の log を見せる攻撃。 ③選択的 anchor — 都合の悪い計算を最初から anchor しない自由（MPR-5 の開示済み限界）。
  • どう塞ぐか: anchor log の head を運営者の支配が及ばない場所へ定期的に刻む（公開 git・Zenodo・ 他の KairosChain インスタンス（相互係留）・RFC 3161 時刻認証局 等）。log を作り直した瞬間、 再計算 head ≠ 外部に残る head で露見（ANC-4）。見せ分けは独立した読者同士の head 突き合わせで検出（ANC-6）。
  • cadence が本質: 一度でなく律動として刻み続ける。刻みが密なほど、記録を後から挟み込める時間の窓が狭まる （constitutive note §7 の姿勢）。結果非依存で anchor する規律の機構化もこの段の仕事。 その際、凍結 ANC v0.5 の human-gate 非目標（自分の著作物の anchor は人間の行為）と衝突しない形 （監査用の鎖 head の自動係留と著作物の人間ゲートの区別）で設計する（R1 の教訓・handoff 記録済み）。
  • 無限後退の閉じ方: 「anchor サーバーを誰が anchor するのか」は、より深い権威でなく インスタンス同士が互いの head を普通の anchor entry として刻み合う相互係留で閉じる。 鎖の head も「ただの digest」なので L1 の証明の形は不変。

L3 — 独立監査人による再実行と foreign 署名（reproduces）

  • 塞ぐ穴: L1+L2 でも証せるのは「記録した・書き換えていない・この順序」まで。 計算の中身の正しさは語らない（MPR-6 の線引き）。さらに現状の anchor は same_party＝運営者の自己申告（ANC-8）。
  • 第一段 — 材料の by-reference 記録: 計算の {入力・コード・実行環境イメージ・出力} を、 中身は鎖に載せず指紋だけで内部鎖に記録（BRD-2 の作法）。 「再現性」が検証可能な主張になる: 記録どおり再実行して出力の指紋が一致するかを見ればよい。
  • 第二段 — 第三者の署名: NDA を結んだ独立監査人が closed 環境で再実行・一致確認し、 公開 anchor に reproduces attestation を自分の identity で署名して載せる。 ANC-8 の relation 導出により、監査人の署名は自動的に foreign（第三者の裏書き）と表示される。 自己申告が第三者の証言に変わる瞬間。
  • 限界: 監査人の独立性は identity 発行に依存（ANC-8 開示済み）。再実行で検証できるのは決定的な計算のみ。 実行環境の同一性の担保が実務上の急所。それでも L4 と比べ桁違いに現実的＝当面の現実解。

L4 — 選択的開示（実装済）とゼロ知識証明（次段）

  • 塞ぐ穴: L1〜L3 は主張を検証させるのに対象を指し示して見せる前提だった。 競争環境や患者データでは、この「見せる」こと自体が漏らせない。
  • 実装済（sdp-1・内容目隠し）: 記録の欄の値を塩付き指紋で伏せたまま、 「この形式の記録が存在する」「この裏書き人がこの判定を主張した」「適合条件を満たした 再現裏書きが立っている」を検証させる。署名は記録の指紋だけで検証できる（map-1 §1.1）ので 内容を見せずに済む。ただし伏せるのは値であって「どの記録か」ではない （指紋・欄名は公開）。設計 v0.3 FROZEN・gem 3.47.0。詳細は aud_l4_sdp1_implementation_report_ja_20260722.html。
  • 次段①（sdp-2・どの記録かも隠す）: 証明系を選んで「封印 root の中のある葉を 知っている（どの葉かは明かさない）」一員性証明。ここが本来の zero-knowledge の所属証明。 handoff 済（KF）。
  • 次段②（本物のゼロ知識証明の spike・§9.4）: sdp-1 の内容目隠しの上に、 KairosChain 初の本物のゼロ知識証明を再現性の秘匿集約という題材で入れる。 「公開 DOI リストを全部調べた・各点数は秘匿・平均だけ公開かつ正直」を、 個々の点数を明かさずに証明する。ゼロ知識証明は集約統計の範囲証明（range proof）に宿る。
進め方の方針（masaomi 決定・2026-07-21）
  • L3（計算の正しさ・再現性・監査性の検証）は GenomicsChain 側で推進する。 こちら（KairosChain 本体）は L1 実装 → L2 の順でこのまま進める。
  • L2 の信頼は、別の運営者が管理する HestiaChain インスタンスの存在によって積む。 head の刻み先が「運営者の支配の外」であることが ANC-4 の要件であり、 独立運営のインスタンスとの相互係留（federation）はその最も KairosChain らしい実現形。 ANC v0.5 §5 の想定どおり、新しい種は不要——相手インスタンスは「ただの foreign depositor」として振る舞う。

9. L4 の先へ — 「データを見せず再計算可能を証明」の現実解（2026-07-22 追記）

L4（ゼロ知識証明）の議論を深めた際に、「入力データを誰にも見せず・第三者に再実行させずに、 その計算が確かに行われたことを証明したい」という理想が焦点になった。ここでは、その理想を 今日の技術で近似する二つの道具（TEE と zkVM）と、GenomicsChain としての現実的な進め方を記録する。 なお正本の凍結設計（AUD-L3 v0.4・RPR-1..5）は変更していない。以下は将来スライスの方針メモである。

9.1 TEE と zkVM — 同じゴールを正反対の信頼基盤から狙う

まず大前提として、TEE も zkVM も「計算を最低一回は実際に走らせる」。「走らせずに証明する」のではない。 違いはどこで走らせ・誰に中身が見え・何を信頼の根にするかである。

  • TEE（Trusted Execution Environment: Intel SGX / AWS Nitro Enclave / AMD SEV-SNP / Intel TDX）: 持ち主（root）にも中を見せない隔離領域（enclave）の中で計算を走らせ、CPU が 「測定値 M（＝ロードしたコードの hash）の enclave が本物の環境で動き、この出力を出した」を ハードウェア署名する。この署名済み証言（attestation quote）を記録・anchor する。 信頼の根はCPU ベンダー。
  • zkVM: prover が入力を見て計算し、入力を一切漏らさない数学的証明を作る。信頼の根は数学のみ。 ただし証明生成コストがネイティブの数万〜数十万倍で、ゲノム規模のパイプライン全体には現状非実用。
「TEE ＝ ベンダー固有の zkVM」か？ — 惜しいが肝心の一点で違う 「検証可能実行」という目的は同じで、そこは良い喩え。だが監査ではこの差が本質: TEE の保証はハード条件付き（side-channel 脆弱性や鍵漏洩で崩れる）＝ベンダーとシリコンを信じる、 zkVM の保証は無条件に近い＝誰も信じない。よって別物として扱う: 「TEE ＝ ハードウェアが保証する実行／zkVM ＝ 暗号が保証する実行」。 TEE はシリコンを信じる代わりにほぼネイティブ速度を得て、zkVM は速度を犠牲に「誰も信じない」保証を得る。 （両者は排他でなく合成可能——zkVM prover を TEE 内で走らせて速度＋多層防御を狙う研究もある。）
観点Docker / EC2 / Thoa（通常）TEEzkVM
データが見える相手持ち主（root）・クラウド事業者enclave 外は誰も見えないprover のみ・証明は無漏洩
外部への実行証明なしハード署名 attestation暗号 proof
信頼の根運営者＋事業者CPU ベンダー（条件付き）数学（無条件に近い）
速度ネイティブほぼネイティブ数万〜数十万倍重い

インフラとの関係: TEE は Docker/EC2/Thoa の代わりではなく下（中）に敷く機能。 Docker は「環境を固定して再現性を出す」土台として今のまま活き、その内側の enclave で 「秘匿＋証明が要る仕事だけ」を走らせる。EC2 なら Nitro Enclaves が既に使える。 Thoa が TEE を提供できるかは backend が confidential-computing 対応ハードか次第（Thoa 側に要確認）。

9.2 GenomicsChain としての進め方 — 主張ごとに道具を割り当てる

一つの機構に全部やらせない。証明したい主張を分け、それぞれに最適な道具を当てる。 土台はいずれも既に実装・検証済みの AUD-L1 累積 commitment（＝下記③のパターン）である。

証明したい主張道具状態
入力/pipeline/出力が主張時点に存在し差し替えられていないAUD-L1 累積 commitment実装済
独立した誰かが決定論 pipeline を再実行し同じ出力を得たAUD-L3 再現裏書き（裁定＝人 or TEE）実装済（TEE 接続は将来）
入力を見せず・再実行させず「output = f(input)」を証明TEE（今実用・ベンダー信頼）／ zkVM（純暗号・重い）将来スライス
中身（欄の値）を見せず「この裏書きが存在・この判定を主張」を証明AUD-L4 選択的開示（sdp-1・内容目隠し）実装済（gem 3.47.0）
ゲノムを見せず「バリアント X の有無」だけ証明関心領域切り出し＋小 zkVM 回路AUD-L4 圏・将来
どの記録かすら明かさず一員性を証明AUD-L4 sdp-2（本来の zero-knowledge 所属証明）handoff 済（KF）
N 件を全部調べた・各点数は秘匿・集計だけ公開かつ正直Pedersen commitment ＋ range proof（初の本物ゼロ知識証明・§9.4）設計メモ済・spike handoff 済

zkVM をビッグデータに使う3つの定石（外部 AI 提案の評価）: いずれも本物で組み合わせ可能。 ①重い計算はネイティブ・検査だけを zkVM（検査が計算より軽いときのみ有効）、 ②関心領域だけ切り出して zkVM（数KB の述語＝バリアント有無証明。今すぐ実用圏）、 ③Merkle root ＋一部＋包含証明で巨大データの一部を軽量・安全に処理。 重要なのは③は「未来の工事」でなく既に持っていること——本レポート§4-6 の累積 commitment ＋包含証明が まさに③で、①②が差し込む土台が完成している。

混ざりやすい区別（誤ロードマップ防止） 「データについての小さな述語」（②③・①の一部＝今でも実用）と、 「重いパイプライン全体が正しく走ったことの証明」（＝当面 TEE が現実橋・zkVM は将来）は 難易度クラスが違う。②③は「バリアント有無」等の切り出し証明を今すぐ可能にするが、 「FastQC／アライメント丸ごとを再実行なしに正しいと証明」は依然重い。ここを混ぜない。

9.3 二トラックと、当面の判断（masaomi 決定・2026-07-22）

方針
  • トラック1（重いパイプラインの秘匿再現）＝ TEE を AUD-L3 の procedure 裁定手続きに据える。 SUSHI FastQCApp の決定論性（入力・image・版・パラメータが実行前に確定）が 「事前 committed で結果非依存の裁定手続き」になり、RPR-3/RPR-4 の不変量とそのまま噛み合う。 実際の再現環境（Thoa/EC2）が整ってから設計・実装・テストする。特に企業 pilot で提案するのが最適。
  • トラック2（述語・適格性の秘匿証明）＝ 関心領域切り出し＋小 zkVM を AUD-L4 選択的開示と組む。
  • 当面（TEE 不要）: BioRxiv 論文の再現性チェックは公開データゆえ秘匿不要。 AUD-L1（anchor）＋ AUD-L3（再現裏書き）だけで、統計を genomicschain.ch で公開し論文化まで到達できる。 真の工数は attestation でなく生命情報の再現作業そのもの（各 pipeline を決定論的に走らせる）。 AUD-L4（選択的開示）は「個々の論文の合否を名指しせず集計だけ出す」著者保護に効く任意の上乗せ。

この追記の詳細な議論記録は L2 context tee_zkvm_verifiable_computation_discussion_20260722。 AUD-L3 の procedure 裁定への TEE 差し込みは AUD-L4 handoff の backlog 注記 （handoff_aud_l4_zero_knowledge_design_20260722）に「非目標候補のまま保持・pilot 時に目標へ格上げ」として記録。

9.4 次の主眼 — KairosChain 初の本物のゼロ知識証明（再現性の秘匿集約）

ここまでの L1〜L4 には、まだ本物のゼロ知識証明が一つも入っていない （sdp-1 は塩付き指紋による内容目隠しで、ゼロ知識証明ではない）。次の主眼は、 上の 9.3「当面（TEE 不要）」で触れた著者保護の上乗せを、初のゼロ知識証明として実装する試作である。

示したいこと:「この公開 DOI リスト（例: BioRxiv 1000 本）を 全部再現チェックした。個々の論文の点数は明かさない（名指し批判を避ける）。 だが全体の平均再現性は M% で、この数字は正直だ」——を、 どの論文が何点かを一切見せずに証明する。

これは sdp-1（内容目隠し）とも sdp-2（どの記録かを隠す）とも別の機構である。 DOI は公開・伏せるのは点数・ゼロ知識証明は集約統計に宿る。 主張は四つに分かれ、本物のゼロ知識証明が要るのは最後の一つだけ。

主張道具ゼロ知識か
C1 1000 本全部調べた（被覆）公開 DOI ごとに署名付き rpr-1 裏書き（点数は sdp-1 で目隠し）否
C2 個々の点数は秘密Pedersen commitment（鍵つきの箱＝中身が見えない）否（箱に入れるだけ）
C3 公開平均は秘匿点数から正直に計算（Phase 1）箱どうしを足せる性質で「合計の箱」を開ける弱い（合計を開くだけ）
C4 各秘匿点数は正当な範囲の値だ（Phase 2）range proof＝箱を開けずに「中身は 0〜100」を証明はい（本物のゼロ知識証明）

なぜ Phase 2（range proof）まで要るか: Pedersen の箱にはどんな値も入る （範囲を縛らない）。Phase 1 の合計開示だけだと、真の平均 8 点を、999 本は本物＋1 本に 32000 という範囲外の値を入れて平均 40 に偽装でき、しかも合計の検証は通ってしまう。 Phase 2 は各箱に「中身は 0〜100」の証明を値非開示で課し、範囲外の 32000 は証明が作れず弾かれる。 「隠した値の性質を、値を明かさずに証明する」——これがゼロ知識証明の定義そのものであり、 KairosChain 初の本物のゼロ知識証明はここ（C4）に入る。両 Phase がそろって初めて、 公開平均が秘密でありながら信頼できる数字になる。

正直な狭さ（試作を見せかけにしないために）
  • 集約が正直なのは「箱に入れた点数」に対してだけ。その点数が本当の再実行結果かは 証明しない（RPR-4/MPR-6 の残余・ゼロ知識証明でも消えない）。
  • 「1000 本やった」は「1000 個の署名付き裏書きを commit した」であって「1000 回走らせた」ではない。
  • DOI リストは結果を出す前に AUD-L1 で係留しておく必要がある（差し替え防止）。
  • この試作で初めて anchoring に非自明な暗号部品（楕円曲線の群演算）が入る。 従来の「sha256＋Ed25519 だけ」からの意図的逸脱として明示する（trusted setup は不要）。

TEE 本格実装ではなく、commitment＋range proof で秘匿集約を実現する軽量路線。 詳細は設計メモ aud_l4_zk_aggregate_reproducibility_spike_design_v0.1.md と handoff（L2 handoff_aud_l4_zk_aggregate_reproducibility_spike_20260722）。 Phase 1／Phase 2 は別セッションで実装する。
