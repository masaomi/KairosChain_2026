## 1. Purpose

KairosChain gains a project-management capability (a SkillSet) and a secretarial disposition (an instruction-mode layer) so that an operator can plan, track, and be reminded of project work through the same MCP surface used for all other KairosChain interaction.

The first managed project is KairosChain development itself: the instance that hosts the capability is also its first subject. This is deliberate **self-application** (Prop 7 — the system's own development becomes an object it acts upon and validates against), not a claim that the capability closes a self-referential loop at the definitional level. Consistent with partial autopoiesis (Prop 2), the loop is deliberately left open at the execution layer: the SkillSet manages *data about* KairosChain's development without acquiring authority to redefine KairosChain (INV-PM-5). Self-application doubles as the validation environment — the capability earns promotion into the gem only after surviving real use on its own development.

## 2. Central design tension

Two requirements coexist and must not collapse into each other:

- **Self-application**: the first deployment manages KairosChain development, whose work items are saturated with KairosChain-specific structure (design freezes, multi-LLM review rounds, L1 promotions, gem releases).
- **Genericity**: the SkillSet and mode must be usable, unchanged, for general software development and research projects.

Resolution by separation: the capability defines a domain-neutral vessel; everything KairosChain-specific enters as *content* (data and instance-local knowledge), never as *structure* (schema, tool contracts, mode text). This is the same vessel/inhabitant separation that governs core vs. instruction mode (Scaffolding Stance). The vessel must be generic without becoming empty: minimality (INV-PM-7) and genericity (INV-PM-1) are a tension pair — a schema reduced to identity+status is trivially generic and trivially useless, so each invariant is checked against the other, not in isolation.

## 3. Placement

| Element | Layer | Rationale |
|---|---|---|
| project_manager SkillSet (tools + storage) | Instance-local SkillSet (`.kairos/`), Phase 1 | Selective survival: validate on real use before gem promotion |
| Secretary mode document | Instruction-mode layer, composes with an existing instance constitution | Disposition is per-operator; capability must not depend on it |
| Project/task data | Instance-local project store | Project state is operational memory, not framework knowledge |
| Decision records | Attestation chain | Constitutive recording of irreversible project decisions (Prop 5) |

## 4. Invariants

**Definition used below — irreversible project action.** An action is *irreversible* when it meets **either** of two triggers: **(i)** it mutates an external party's expectation — creating, changing, or withdrawing a commitment communicated outside the project; or **(ii)** it disposes of an adopted internal artifact or direction — abandoning an adopted plan, changing the *project-level* scope, retiring an authoritative store (INV-PM-6), or discarding a major design direction — *such that the disposal cannot be undone by an ordinary state transition*. The primary, checkable test of trigger (ii) is that reversibility clause; "adopted" and "load-bearing" are glosses that describe the kind of thing the clause catches, not independent tests. Everything else — a task advancing its status, an internally-set review date shifting, an item's description or estimate being edited, a single work item quietly dying (selective survival) — is *routine*. INV-PM-3 (what is recorded constitutively) and INV-PM-4 (what requires a human gate) both refer to exactly this one two-trigger boundary, so the recording line and the gate line are the same line.

**INV-PM-1 (Genericity of structure).** The task and project data model, tool contracts, and secretary-mode text contain no vocabulary specific to any managed domain. Domain binding occurs only through data content and instance-local knowledge entries.
*Justification:* This is the only stable way to satisfy both requirements of §2. A single leaked domain term in the schema (e.g., a "review_round" field) would make every future domain a second-class tenant. Checked jointly with INV-PM-7 (see §2): genericity must not be bought by emptying the vessel.
*Test:* the design passes if a researcher managing a wet-lab project and an engineer managing a generic software project could both adopt the SkillSet editing only their own data and knowledge entries.

**INV-PM-2 (Capability/disposition separation).** Removing or replacing the secretary mode leaves the SkillSet fully functional; removing the SkillSet leaves the mode inert but harmless. Neither references the other's internals — the mode invokes the SkillSet only through its public tool contracts, and any operator-specific heuristic in the mode (§5) must be expressible through the generic capability surface (§6), never through a domain-specific field added to the schema.
*Justification:* mirrors the core/mode separation. A tutorial-mode user gets the capability without masaomi's secretarial disposition; a different operator can author a differently-tempered secretary over the same tools. The back-door risk — a mode heuristic silently requiring a bespoke field — is closed by requiring expressibility through the generic surface.

**INV-PM-3 (Recording discipline, two-tier).** Irreversible project actions (as defined above) are recorded constitutively (attestation, with provenance). Routine state changes are recorded only in the instance-local project store, never on chain.
*Justification:* Prop 5 (constitutive recording) is realized concretely by the two triggers above, not by every checkbox. Trigger (i) is stated as *mutation* rather than a one-time "commitment" event, so both the original commitment and any later change or withdrawal of it leave a trace — a record that showed the commitment but not its renegotiation would misrepresent what was promised. Trigger (ii) is what makes the internal-but-irreversible acts constitutive without appeal to external parties: retiring an authoritative store or discarding a major design direction leaves a trace even though no outside party's expectation moved. Chain noise from routine transitions would erode the signal value of constitutive records (same reasoning as the L2-attestation activation policy). A single work item quietly dying (selective survival) is routine and is not recorded; disposing of an adopted direction or the *project* itself satisfies trigger (ii)'s reversibility clause and is recorded. Per Prop 5 this record is *constitutive*, not evidential: the attestation does not document a decision that already exists independently — the recorded act is part of what makes the decision the project's decision. "Leaves a trace" above is shorthand for this constitutive act, not a claim that recording merely witnesses a prior fact.

**INV-PM-4 (Proposal, not commitment).** Secretary behavior is proposal-shaped: it surfaces, reminds, drafts, and asks. It never autonomously performs an irreversible project action (as defined above); every such action passes through a human gate.
*Justification:* a secretary that commits on the principal's behalf has become a principal. The trust model here is assistant, not delegate. The human gate is the procedural floor's requirement that irreversible actions remain under human authority; naming that boundary once (the definition above) is what makes this invariant checkable rather than a list of examples.

**INV-PM-5 (Layer discipline).** project_manager tools read and write only the instance-local project store and attestations. They never write L0 or L1. The project store is a *separate authority* from L2 session contexts: a work item may link to an L2 context as provenance, but L2 never holds project/task state and is never a second store of it (this keeps INV-PM-6's single-authority claim intact across layers). Insights arising from project management that deserve L1 status travel the normal L2 → L1 promotion path with human approval.
*Justification:* the SkillSet manages work *about* the system without acquiring authority *over* the system — required for safe self-application (§1, §2). Keeping project state out of L2 prevents the project store and session memory from becoming two authorities for the same facts.

**INV-PM-6 (Single authoritative store, with bounded transition).** Exactly one store is authoritative for project/task state. This is a *data-authority* claim (a sharp operational boundary), not an ontological one — it does not contradict the P2P/no-global-authority development guideline, which concerns system governance, not the location of a single project's operational state. During migration the transition is explicitly bounded: any prior record of the same state (e.g., a session-memory resume index) becomes read-only at cutover, serves only as a migration source, and is retired — frozen or deleted — once the new store has run without divergence across a declared observation window. Migration *preserves each item's original last-meaningful-touch marker* (carry, not restamp), so seeding does not falsely refresh recency and blind dormancy detection at the very moment the new store takes over; the store-retirement record is one attestation about the store, never a per-item touch. That retirement is itself an irreversible project action and is recorded per INV-PM-3.
*Justification:* dual authority is how reminder systems silently rot; the known failure mode (stale resume points diverging from actual state) is the very problem this SkillSet exists to fix. Declaring a "view" without enforcing read-only and without a termination condition would reproduce that rot, so single authority must be *enforced and time-bounded*, not merely declared.

**INV-PM-7 (Data model minimality).** A work item carries, at minimum: identity; a status within a declared lifecycle that includes an *awaiting-gate* state (an item paused pending a human decision); an optional salience signal (a coarse importance marker, not a full priority scheme); optional temporal commitments (deadlines, review dates); optional *blocking dependencies* — each a blocking relation to something the item cannot advance without, namely another work item or an external world-event (a sequencing run, a reagent, a collaborator's deliverable), resolved when the referent completes; an optional *assignee* — a bare reference to the agent responsible for the item, a different relation from a blocking dependency (it answers "who holds this," not "what is this waiting on"), unset in the single-operator degenerate case; and provenance links (to L2 contexts, attestations, or external artifacts). No other field is required by structure. Anything else is open content. *Dormancy is not a field* — it is derived from each item's *last-meaningful-touch* marker: the time of the newest operator-meaningful change to the item (a status transition, a content edit, a constitutive record), explicitly excluding bulk, migration, and mechanical writes.
*Justification:* every field beyond this set is a bet on a domain, and minimality is what makes INV-PM-1 checkable — but the set must be sufficient for the behavior §5 promises. Salience supplies *importance* and the derived last-meaningful-touch supplies *dormancy*; together they let the digest surface "dormant-but-important" items, which a deadline-only sort cannot (deadline-free items — the common case in research and in KairosChain's Keep-Fire embers — would otherwise go dark). The marker must key off *meaningful* touches, not raw store writes: a bulk migration or reformat that touches an item without an operator-meaningful change must not reset its recency (that is the case that defeated the v0.3 derivation), and conversely a routine status change — recorded store-only, not on chain — must still count, so the marker cannot key off attestation timestamps alone. Which touches count is a property fixed here; the concrete write-classification is mechanism (§11). Blocking dependency and assignee are kept as *separate* fields deliberately: folding assignment into a "generalized dependency" conflated two different queries ("what is this waiting on" vs. "who owns this") and imported a meaning that self-assignment cannot carry (an agent does not block itself). Two honestly-named optional fields are more minimal than one field secretly carrying two semantics. Assignee is a bare data *slot*, not multi-operator support: it carries no permission, routing, ownership-transfer, or visibility semantics (those are the multi-operator concerns §9 defers); an always-optional, unset-by-default reference costs the single operator nothing and does not pre-build the deferred domain. World-event referents are operator-cleared, not system-resolved — the invariant does not promise automatic resolution for them.

## 5. Secretary mode — behavioral charter

The mode document is thin and expresses disposition only. The items below are **illustrative of one operator's (masaomi's) disposition, not structural requirements** — a different operator authors a differently-tempered secretary over the same capability (INV-PM-2):

- At session start, surface what needs attention — commitments now due or approaching, items awaiting a human gate, and dormant-but-important items — in a few lines, not a dashboard dump. (This is the disposition that consumes the salience and awaiting-gate state of INV-PM-7.) When surfacing dormancy, distinguish a *neglected* item from one *legitimately waiting* (blocked on a dependency, or parked in awaiting-gate): the schema already carries the discriminating data (blocking dependency + awaiting-gate status + last-meaningful-touch), so a long-blocked item can be surfaced as "still blocked" rather than as neglect — otherwise the digest reads noisy.
- Keep important-but-dormant items from going dark by proposing a minimal heartbeat action rather than silence (the operator's Keep-Fire heuristic).
- Report what is healthy, not only what is late (Ordinary Happiness); deliver bad news situated, never omitted (Non-Omission).
- When an item is stalled, surface both the deprioritize option and the invest option; do not default to friction reduction.

Everything above composes with, and defers to, the active instance constitution. The charter adds secretarial behavior; it introduces no new values.

## 6. Capability surface (properties, not signatures)

The SkillSet provides operations sufficient to: register and evolve projects and work items through their lifecycle; query by status, salience, temporal proximity, and dependency; produce a status digest over such a query (who consumes the digest — a secretary at session start, a Web UI later — is an inhabitant concern, not part of the capability); and record an irreversible project action constitutively with provenance. Mechanism choices (tool names, store format, query shape) are implementation-phase decisions — see §11.

## 7. Self-application plan (first inhabitant)

The plan is governed by two invariants rather than a fixed procedure: the migration preserves single authority through a bounded, read-only-enforced transition (INV-PM-6), and the observation that follows tests whether the vessel is sufficient (does session-start surfacing beat the old index; do the minimal fields of INV-PM-7 suffice; does the recording boundary of INV-PM-3 sit at the right altitude). Observation outcomes feed the promotion decision (§10) — or the SkillSet's death, which is an acceptable outcome (selective survival). Migration and seeding tooling is a mechanism (§11).

## 8. Relation to existing components

- **Attestation chain**: reused as the constitutive-recording substrate; no new ledger.
- **agent / autonomos SkillSets**: out of scope as executors. The secretary reminds humans; it does not schedule autonomous work. Composition with autonomous loops is future work and gated by that track's guard design.
- **pdca_review L1**: the secretary can surface a due review; the review discipline itself stays in its own L1.

## 9. Out of scope (this design)

Web UI routes, Teams integration, multi-operator/multiuser semantics, and any in-Ruby LLM judgment. The Web UI phase will require gem-side changes and its own design round, including the boundary question of what authority a non-Claude-Code conversational surface may hold (current stance: read + task operations, never layer writes).

## 10. Promotion criteria (instance-local → gem)

Promote to gem templates only when: the SkillSet has survived sustained real use on KairosChain development; at least one genericity check against a non-KairosChain project (even a paper exercise) has passed INV-PM-1; and the data model's changes have become content-driven rather than structure-driven (i.e., new needs are met by new content and knowledge entries, not new fields). Until then it remains in the instance repository.

## 11. Backlog (mechanism candidates, non-binding)

- Store format and location for project/task data (single file vs. per-project; format choice).
- Tool naming and granularity; digest formatting; the concrete salience scale.
- Migration and resume-point seeding tooling; the divergence check and observation-window length for INV-PM-6. Seeding must set each item's initial last-meaningful-touch marker from the *source's own recency signal* (e.g., a maintained resume index's last-update time), never from the migration write-time; for a markerless source (one with no per-item recency), the item seeds as *non-dormant until its first meaningful touch* — this avoids both false-refresh and false-dormancy at cutover (the first inhabitant's resume index predates the marker concept).
- The concrete classification of writes into meaningful vs. mechanical for the last-meaningful-touch marker (INV-PM-7).
- Dependency-cycle handling; recurring-commitment representation.
- Web UI (`/pm`) and Teams webhook designs (each its own design round).
- Optional composition with pdca_review scheduling.
