## §1 Scope and Position

This design adds one thing to the Meeting Place: an anonymous, read-only web presentation surface for SkillSet deposits, so that a human with a browser can see what SkillSets — including certified distillates — are listed, on the same footing as the existing skill catalog. Today the two deposit lineages diverge: skill deposits have a public web catalog, while SkillSet deposits are reachable only through the authenticated agent API. The divergence is an accident of construction order, not a design decision, and this surface closes it.

The design is presentation-only. The exchange's deposit, browse, content, and withdraw interfaces, its storage, and the hestia skill catalog are consumed unchanged. One extension of existing machinery is named openly rather than smuggled: the place-extension registration mechanism, today capable of declaring only authenticated API routes, is generalized so an extension can also declare unauthenticated public routes served under the Place's established public-access discipline. That generalization is the only mechanism-level change this design requires of infrastructure it does not own.

This surface is adjacent to BL-S2-7 (the attestation-carrier exposure surface of the frozen slice-2 design) but does not resolve it. The catalog presents listings; the carrier answers revocation queries. The catalog may point at the carrier once BL-S2-7 is resolved; until then it must not simulate the carrier's answers. One constraint this surface does impose on BL-S2-7 is named openly: certificate identities of deposited distillates become anonymously discoverable through the catalog, so any BL-S2-7 resolution of per-certificate reachability isolation cannot rest on identity secrecy for deposited certificates and must rest on something else. This follows from CD-8's release of listing identity at deposit approval together with this surface's own anonymous-audience decision; the catalog accordingly promises presentation discipline, not addressability obscurity.

## §2 Inherited Invariants (constraints on this design, unchanged)

- **CD-2** (checkability vocabulary): certificate claims carry a disclosed checkability status — checkable / anchor-pending / trusted. The surface renders that vocabulary; it never invents a stronger one.
- **CD-3** (provenance is not quality): origin-only claim vocabulary; the quality channel is separate. The central constraint on this surface.
- **CD-5** (evidence under selective disclosure): the certificate is evidence about records, never a republication of them. Read here as: the certificate summary is a projection of an artifact already constrained by CD-5, and the summary can only narrow, never widen, what the certificate discloses — this is what makes the certificate's claims safe for any audience, and it is the load-bearing premise of WC-3's disclosure bound.
- **CD-8 / CD-11** (snapshot vs carrier; revocation observability): the in-package snapshot is frozen at packaging; revocation state is chain-authoritative and carrier-mirrored; absence of revocation is never provable. The revoker's duty to update listings under their control is consumed unchanged — a withdrawal this surface reflects may be that duty executing. The surface must not present anything that outruns these semantics.
- **CD-10** (guard enrollment of writers): every persistent-store writer the distribution path introduces within the depositing instance's own boundary is enrolled with the confidentiality guard. Read here as: the same enrollment discipline, applied at whichever instance's boundary the writer runs within. Cited so the enrollment claims in WC-1 and BL-WC-5 are checkable from this document.
- **DEE** (no ranking): the Place's catalogs are unordered random samples. Already honored by both existing catalogs; this surface inherits it as a constraint, not a choice.

## §3 New Invariants

### WC-1 — Public window discipline

**Invariant.** The catalog surface is read-only and unauthenticated; no anonymous request causes a persistent write to exchange or catalog state, and the surface grants no new authenticated capability. The composed surface — hosting window and extension together — satisfies the Place's established public-access discipline: rate limiting, method restriction, and transport-level response discipline are contributed by the hosting window, and context-correct escaping of everything rendered is owned by the extension that renders it — including content-derived values that land in transport contexts such as addresses and response headers — held to the same public-window standard.

Read-only on the anonymous path is what makes the surface cheap in guard terms: a request path that writes no exchange or catalog state introduces no new domain writer, so CD-10 has nothing new to enroll on that path; operational window state that the anonymous path may touch — rate-limit counters, access logs — belongs to the existing window discipline and remains governed there, under CD-10 where applicable, rather than being smuggled out of scope by this design's vacuity claim. Any writer this design's mechanisms introduce elsewhere (see BL-WC-5) remains under CD-10 as usual, and a surface that grants no capability cannot widen the deposit or withdrawal attack surface. The discipline is inherited rather than re-invented because the Place already operates an anonymous window with rate control; a second, differently-disciplined anonymous surface would be a new security posture to review, whereas a second consumer of the same discipline is not. Escaping sits with the extension and not the window because escaping is context-sensitive — correctness requires knowing where each value lands in the rendered output, which is exactly the content knowledge WC-2 forbids the window from holding; the same reasoning covers content-derived values in transport positions, which is why the duty follows the content, not the layer.

### WC-2 — Presentation ownership follows listing ownership

**Invariant.** The semantics of a SkillSet listing — what a deposit is, what its metadata means, what its certificate summary contains, and how any of it is rendered — are owned by the exchange extension that owns the listings; the presentation surface is registered by that extension through the generalized public-route declaration, and the hosting window contributes only the transport-level discipline of WC-1. No component outside the extension acquires knowledge of SkillSet package internals. The generalized mechanism carries two properties by construction, not by consumer convention: public routes declared through it are read-only on the anonymous path in WC-1's sense — no route-declared persistent domain write; operational window state remains the window's — a property of the mechanism itself, so no future extension can declare an anonymous writing route through it, and a public-route declaration is a recorded act, checkable at registration time, by which the declaring extension binds itself to its own disclosure invariants under WC-1's window discipline.

The Place's extension mechanism exists so that the host does not accumulate per-extension knowledge; a SkillSet page implemented inside the host would reverse that and make every future package-format change a host change. Generalizing route declaration keeps the boundary: the host learns that an extension has public routes, never what they mean. Because the host is thereby structurally unable to police what a public route discloses, the constraint is placed where structure can hold it — read-only is made constitutive of the mechanism, which the host can enforce without content knowledge, and the disclosure obligation is attached to a recorded declaration, mirroring CD-10's discipline of enrollment-before-exercise for a capability whose blast radius (anonymous audience) exceeds a writer's. What remains normative rather than structural — the honesty of the declaring extension's own disclosure judgment — is exactly the residue partial autopoiesis locates at the governance level. The registration surface's concrete shape, including the recorded-declaration form, is backlog (BL-WC-1).

### WC-3 — Anonymous disclosure bound

**Invariant.** What the anonymous surface reveals is bounded by: listing metadata already served by the authenticated agent browse interface, plus a certificate summary consisting exclusively of the certificate's own claims and their checkability status, as judged at the deposit crossing. The summary never re-exposes content derived from the package payload beyond what the certificate itself states — it is a projection of a CD-5-constrained artifact and can only narrow it. Package content never crosses the anonymous surface, and acquisition remains exclusively on the authenticated agent path — the surface may describe how to acquire, never perform it.

The bound is set where deposit approval already did the judging: a deposit crossing that the guard approved has released its listing identity and its certificate's claims into distribution, so showing them to a browser widens the audience, not the disclosure. The summary is anchored to deposit-judgment state so that what it asserts is exactly what crossed under guard judgment — whatever the deposit crossing verified is what the summary reflects, and no stronger claim is manufactured by the rendering. Package content is different in kind — it was released to acquirers under the authenticated path's identity and recording semantics, and the anonymous surface must not create a second, unrecorded acquisition channel. Deposits approved before this surface exists become anonymously visible at its launch; that is entailed by the deposit-approval-releases-listing-identity principle, not a new crossing. The attestation board already publishes anonymously under the same reasoning; this invariant extends the precedent, not the exposure. Which certificate fields constitute the summary is backlog (BL-WC-2), selected under CD-5 as the bound on admissibility.

### WC-4 — Provenance-neutral rendering

**Invariant.** The provenance field is populated exclusively from certificate-derived state; depositor-authored metadata is rendered in a register structurally distinguishable from certificate-derived fields, so no depositor text can occupy or structurally imitate the provenance register. The field has three truthful states, each rendered as itself: a summary (certificate present, summary available); "no provenance claim" (no certificate in the judged package); and a neutral, non-diagnostic unavailability marker (certificate present, summary not available) — the surface never renders a certificate-bearing listing as asserting no provenance claim, and never renders diagnostics in the field. A certificate is rendered as a provenance field, co-equal in placement across all listings; the surface offers no ordering, badging, filtering, sampling bias, or visual emphasis keyed on certificate presence. The surface may offer search over depositor-authored metadata; no query or search parameter selects on, or matches against, certificate-derived fields, and any index excludes them, including rendered summary text.

This is CD-3 landed on a rendering surface, and it is the invariant most at risk from good intentions: a "certified" badge, a certificates-first sort, or a certified-only filter each read as helpfulness and each convert an origin claim into a quality signal. The same conversion is available from below — a depositor whose description announces "certified, provenance verified" would forge the register if depositor text and certificate-derived fields were structurally indistinguishable — and from the side: a search box that matched certificate vocabulary would hand back the certified-only selection the surface refuses to offer. The design's answer to all three is the same: uniform structure with a single provenance register that only the machinery can populate. What this forecloses is precisely what the surface controls — its own ordering, selection, and registers. A client that walks published listings and sorts them for itself is outside any rendering design's power and outside this one's claims; that residual is the same one the attestation board accepted, and §1's posture — presentation discipline, not addressability obscurity — already owns it. The unavailability marker exists because absence of a summary and absence of a claim are different facts, and a surface whose defining commitment is status honesty must not collapse the one into the other — the marker's failure direction is CD-3-safe (it understates), but understating is still misstating, so the state is named and rendered as itself. The DEE random-sample discipline applies identically to certified and uncertified listings: an unranked catalog that quietly over-samples certified entries would be a ranking.

### WC-5 — Status honesty

**Invariant.** The surface renders certificate status only in registers the underlying machinery supports: checkability per CD-2's vocabulary, and revocation per CD-8/CD-11's semantics — it never asserts non-revocation, never presents the deposit-time certificate summary as current, and disclosed with the summary is that everything in it, checkability status included, reflects deposit-judgment state and is silent about everything after; until the carrier exposure surface exists, the surface states that revocation checking is out of its scope rather than answering in the carrier's place. A withdrawn deposit leaves the catalog; its disappearance is presented as absence of a listing, never as a statement about its certificate. No caching layer this design controls serves a listing beyond the deposit it describes — cache lifetime is bounded by listing lifecycle, and cache-correctness of rendered listings is owned by the extension symmetric with escaping, the window contributing mechanism only. Anonymous listing identity never conflates distinct deposit instances: a redeposit or replacement is a new listing identity in every register, address included, whose provenance field derives solely from the newly judged package, inheriting no summary, status, or continuity from any prior deposit under the same name.

The catalog's certificate summary is derived from the deposited package, so it shares the snapshot's temporal character: true at deposit judgment, silent about everything after. Rendering it with a freshness it does not have would manufacture exactly the false assurance CD-8 divides between snapshot and carrier — and a cache that replays a withdrawn listing, or a listing identity that lets a new package wear a predecessor's summary or its address, would manufacture the same assurance by other means, which is why identity is severed in every register: an audience that bookmarked "this address is the certified one" must not find a different package wearing it. Cache ownership follows the escaping logic — lifecycle is listing knowledge, listing knowledge is the extension's, so the duty sits where the knowledge lives. Caches outside this design's control (browsers, intermediaries) may replay a listing beyond its life; that residual is bounded by the page's own self-disclosed temporal character — a stale page cannot assert more than it honestly asserted when fresh — and is further narrowed by response-header discipline (BL-WC-4). The catalog is not a link in CD-11's observability chain: holders reach the carrier from the package they hold, not from the catalog, so the catalog's silence after withdrawal weakens no revocation guarantee. The honest register costs little and keeps the catalog useful for what it is: discovery and human inspection, with verification routed to the carrier and the acquirer-side toolchain. When BL-S2-7 resolves, the detail view points at the carrier (link format: BL-WC-3); the pointer transfers the question, not the answer.

## §4 Backlog

- **BL-WC-1**: Concrete shape of the public-route declaration in the extension registration surface, including the recorded-declaration form (WC-2), and the addressing scheme for listing detail views — which must yield transport-safe identity encodings and per-deposit-instance addresses (WC-1, WC-5). Resolution constraint: WC-2's read-only property must hold at the invocation-capability level, not only at the declaration or method-filter level.
- **BL-WC-2**: Certificate summary field set — which certificate claims appear in the anonymous summary, selected under CD-5 as the admissibility bound (WC-3).
- **BL-WC-3**: Carrier link format in the detail view once BL-S2-7 resolves (WC-5).
- **BL-WC-4**: Rate-limit parameters and cache headers for the new public routes — headers must forbid or tightly bound shared/intermediary caching of listing responses, this being the channel by which WC-5's lifecycle bound is communicated to caches the design does not control (WC-1, WC-5; defaults inherited from the existing window unless measurement says otherwise).
- **BL-WC-5**: Certificate summary extraction point — at deposit time into listing state, or by pre-request materialization from the stored archive. Constraints from the body: any archive-derived summary exists before anonymous request handling begins — no anonymous request may trigger archive parsing; any non-deposit-time extraction is a replay of recorded deposit-judgment state, never a fresh semantic interpretation of the archive; extraction failure yields the WC-4 unavailability marker, never diagnostic content; the launch-time backfill that gives pre-existing certified deposits their summaries is enrolled under CD-10's discipline at its own instance's boundary; and a deposit-time writer falls under the same enrollment as usual per WC-1. Note for resolution: these constraints leave non-deposit-time extraction viable only via pre-computation off the anonymous path, effectively favoring the deposit-time point; and the replay guarantee is only well-defined if the deposit judgment records the extraction basis (a deterministic result, or a pinned procedure over the validated archive) — absent that record, the archive-materialization option collapses into the deposit-time option.

## §5 Verification Scenarios

**Scenario A — Co-equal rendering and neutrality.** A catalog holding certified and uncertified SkillSets is browsed anonymously. Every listing in whatever the random sample contains shows the same structure with a provenance field; the certified entry's summary — verified via its detail view, which is addressable and not sample-gated — shows claims and checkability status in CD-2 vocabulary, structurally separate from depositor-authored text; no badge, filter, or sort keyed on certification exists anywhere on the surface. A listing whose depositor-authored metadata asserts certification renders with provenance field "no provenance claim," visibly distinct from the description text; a certificate-bearing listing whose summary is unavailable renders the neutral unavailability marker, not "no provenance claim" and not diagnostics; metadata and certificate claims containing markup render inert (escaped). A search for terms of the CD-2 vocabulary (e.g., "checkable") does not select certificate-derived fields. Repeated sampling over a mixed population shows certified-entry appearance frequency tracking its population share; the probe must be able to distinguish population-share exposure from a fixed twofold over-exposure at the catalog's expected size — an always-passing probe does not satisfy this scenario (statistical method: implementation's choice). An empty catalog, and a catalog of only uncertified deposits, render as absence of listings and as uniform "no provenance claim" fields respectively, with no global language implying lack, failure, or missing certification (WC-1, WC-4, DEE).

**Scenario B — Disclosure bound, both directions.** An anonymous client attempts to retrieve package content through the catalog surface: no route serves it; the only acquisition path remains the authenticated agent endpoint, whose recording semantics are unchanged. Positively: anonymous catalog and detail output contains only the WC-3 bound — agent-browse listing metadata plus the certificate summary — and no package content, non-summary certificate material, private exchange state, or acquisition-record data. The detail page describes the acquisition procedure without performing any part of it (WC-3, WC-1).

**Scenario C — Withdrawal, redeposit, and status honesty.** A certified deposit is withdrawn. The listing disappears from the catalog; no residual page and no cache under this design's control serves it thereafter; its address ceases to resolve to any listing; nothing asserts anything about the certificate. The SkillSet is then redeposited — once with a different certificate, once with none: each redeposit renders a fresh listing under a new address, whose provenance field derives solely from the newly judged package, with no summary, status, address, or other residue inherited from the withdrawn deposit. The same severance holds for a replacement through the deposit path: the replacement is a new listing identity, address included, and the rendered summary and the currently listed package are always the pair that crossed a single deposit judgment. Before withdrawal, the detail view never claimed currency — it showed the deposit-time summary with its checkability status and the disclosed limitation that the whole summary reflects deposit-judgment state and that revocation checking is carrier-side (WC-5).

**Scenario D — Deployed composition.** Acceptance includes verification against the deployed production composition, not only the unit harness: anonymous fetch of catalog and detail succeeds end-to-end on the running server; requests outside the read-only method set are rejected; the new routes demonstrably participate in the inherited rate-limiting discipline; the public route is registered by the SkillSet-owning extension through the generalized declaration, with the hosting window contributing no SkillSet interpretation; and an authenticated agent browse returns listings with the same schema as before the public-route addition. This scenario exists because the distribution track has three recorded instances of works-in-tests / dead-in-production wiring failures; a presentation surface whose registration path is new machinery (WC-2) is exposed to exactly that class.
